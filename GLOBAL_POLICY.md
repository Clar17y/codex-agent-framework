# Personal agent routing

Use the installed multi-provider framework at `{{CODEX_ROOT}}/agent-framework/` for coding work. This policy adds provider routing; repository instructions still own worktrees, file ownership, CI and release gates.

- The primary agent owns architecture, decomposition, integration and final synthesis. Keep the user's selected primary model; do not silently switch it.
- Before assigning files or editing, treat the reported example as evidence, not necessarily the full scope. For a bug, trace the cause to its owning component or layer and look for related affected uses; for a feature, identify the intended flow, integration points, and existing reusable components. Choose the smallest complete change, respecting explicit user exclusions and avoiding speculative expansion. Keep this proportional: a quick search and inspection may suffice; use the existing explorer for a bounded investigation when useful. Briefly state the cause or intended behavior, affected scope, chosen location, and any deliberate exclusions in conversation or the task handoff. No separate scope report, persona, or approval stage is needed; surface material scope decisions to the user when necessary.
- Choose implementation, review, and verification effort proportionate to the change's risk and uncertainty. Small, well-understood fixes, including localized behavior changes, can be completed directly with focused checks and self-review. Use independent review or verification when a separate perspective is likely to add meaningful confidence. Security, concurrency, cancellation, timeouts, migrations, data integrity, broad changes, release-critical behavior, and unresolved failures are reasons to consider deeper scrutiny, not automatic triggers for a fixed sequence of agents. Briefly explain the chosen approach in conversation or the PR; a small task needs no separate process record. Repository CI and release requirements remain in force.
- For delegated routine implementation, invoke the `ask-gemini` skill first, using Gemini 3.8 Flash medium through `agy`; check this route before spawning a native Luna fallback. Direct small fixes do not need a provider call or task contract.
- If the adapter returns `fallback_required` (exit 20), spawn a fresh `implementer` on `gpt-5.6-luna` with effort `medium`. Give it the original contract, existing changes, prior output and unfinished checks. This is the automatic routine route while Gemini plan quota is exhausted. Do not ask the user again. Never run Gemini and its replacement concurrently on the same task or overlapping files. Separate tasks with disjoint declared ownership may run concurrently, including within one workspace; directory ownership includes descendants.
- Luna medium is also the pre-authorized fallback when the checked Gemini route is unavailable or blocked, including `blocked_pending_run`; report the actual reason and proceed without another permission question. These failures are not quota exhaustion: do not falsify quota state or clear an unresolved pending run. Before handing over overlapping files, confirm the previous writer has stopped. A pending run in another workspace does not block a fresh Luna task with non-overlapping ownership. This does not bypass Codex permissions or safety review. Failed implementations route to the complex implementer when warranted.
- Complex bounded implementation: `complex_implementer`, Terra low. Planning/adversarial test design: `planner`/`test_engineer`, Sol low. Exploration, docs and refactor audit: Luna medium.
- Implementer handoff: Before handing over implementation, inspect your changes for reuse, clarity, and unnecessary work. Apply justified simplifications within your ownership, preserve observable behavior and others' edits, and rerun affected checks if needed. Include a short summary and check results in the handoff. Perform this pass yourself; separate review or verification is chosen by the primary according to risk.
- When independent review is useful or explicitly required, use `ask-claude` on the integrated change in fresh context, exactly Claude Opus 5, default effort medium. High effort requires a concrete complexity reason and `--review-reason`. Prefer one coherent review over per-writer and whole-branch rounds. Track material findings and their resolution; re-review repairs when uncertainty warrants it. Repeated unsuccessful repairs should prompt reassessment, not an automatic loop. Never silently waive unresolved defects. If Claude is unavailable, use a fresh Astra-low `reviewer` and disclose the fallback. Never use Sonnet or Fable.
- For high-risk work, consider a scoped Sol-high `correctness_gate` when a distinct correctness question remains beyond ordinary review. Use Sol-high `security_reviewer` for explicit security analysis. Choose the depth and sequence for the actual risk; an additional gate is not automatic. Luna max remains exceptional user-requested deep review.
- The primary can run checks directly. Delegate verification when it adds useful independence or substantial parallel work, not merely to obtain a fresh agent. Record the candidate and enough relevant input, command, configuration, and environment context to judge whether evidence still applies. For small tasks, HEAD, the scoped diff/status, and command results usually suffice. Use scoped hashes or aggregate generated-input hashes when reuse or concurrent changes warrant them; avoid exhaustive repository, dependency, ignored-file, or scratch-file inventories. Rerun checks when relevant inputs changed or evidence is uncertain, stale, or missing, not just because ownership or an unrelated commit changed. Keep secrets out of records. Review output is not test evidence.
- Delegate bounded tasks with acceptance criteria, explicit non-overlapping file ownership and validation. Subagents must not delegate again unless authorized by the parent. The integrated batch review is independent of its writers.
- Workers give a concise handoff with completion, blockers, owned paths, decisions, and checks. Avoid routine status chatter and polling. Use one compact run record only when continuity needs it; separate briefs, findings files, metrics, and worker reports are optional. Collect metrics when diagnosing workflow performance or when requested.
- User questions: When asking the user a question, identify which decision depends on their answer. Continue only work independent of that decision. Do not resolve the pending choice or treat silence as approval. If no independent work remains, wait for the user's response.
- Waiting and monitoring: Applies to the primary orchestrator and all subagents. For native subagents, rely on completion notifications; query status only to diagnose a concrete problem or respond to a user request. For Gemini/Claude CLI tasks, prefer waiting for process completion. When polling CLI tasks or CI runs is necessary, use successive intervals of 1, 2, then 5 minutes between checks while status remains unchanged, continuing at 5 minutes thereafter. Reserve longer polling intervals for tasks explicitly expected to take a long time; CI polling remains capped at 5 minutes. Track the next check time per task or CI run. A tool returning early, a host wake-up, or a user-facing progress update does not make another status check due. Check sooner only for a completion notification, actionable error, user request, or known deadline. Reset the backoff when meaningful status changes or a new run starts. Do not send agents routine "still working?" messages. Continue useful independent work while waiting. Respect host limits on individual waits without increasing status-query frequency. Preserve required completion and CI gates.
- For native roles, use installed custom agent definitions when supported. If the host exposes only generic spawning, pass the role's exact model, effort and instructions explicitly; never assume a role label changes the inherited model. Host-supported concurrency limits take precedence.
- The user explicitly authorizes Gemini and Claude CLI bypass/yolo mode for delegated tasks. This bypass is limited to their CLI approval prompts; it does not bypass Codex sandbox or automatic approval review. Keep Claude limited to read/search tools and no MCP, shell, edit or subagent tools. Logs and task contracts belong in the active workspace's `.llm-output/`. Preserve partial edits; never reset or clean them automatically.

See `agent-framework/docs/FRAMEWORK.md` for invocation, reset behavior and validation limits. The archived benchmark figures are historical supplied evidence, not new measurements of Gemini or Claude.
