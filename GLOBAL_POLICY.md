# Multi-provider agent routing

Use the installed multi-provider framework at `{{CODEX_ROOT}}/agent-framework/` for coding work. This policy adds provider routing; repository instructions still own worktrees, file ownership, CI and release gates.

- The primary agent concentrates on scope, architecture, decomposition, ownership boundaries, material decisions, integration, risk assessment and final acceptance. Keep the user's selected primary model; do not silently switch it. Small, well-understood direct fixes (including localized behavior changes) can be completed directly by the primary with focused checks and self-review. For substantial delegated work, assign full bounded outcomes (local investigation, implementation, focused validation, routine repairs, command waiting and interpretation, and self-review) to workers; the primary should not also perform or duplicate that routine execution. Delegate using fresh-context compact contracts with explicit non-overlapping file ownership, concrete acceptance criteria, and validation commands; avoid tiny fragmented assignments and large conversational history or raw log pastes. Forbid overlapping writers: never permit multiple concurrent writers on the same files or overlapping directory scopes; only one writer owns a path at any time. When practical, return related repairs to the existing worker who already owns the files and context rather than spawning a new agent.
- Before assigning files or editing, treat the reported example as evidence, not necessarily the full scope. For a bug, trace the cause to its owning component or layer and look for related affected uses; for a feature, identify the intended flow, integration points, and existing reusable components. Choose the smallest complete change, respecting explicit user exclusions and avoiding speculative expansion. Keep this proportional: a quick search and inspection may suffice; use the existing explorer for a bounded investigation when useful. Briefly state the cause or intended behavior, affected scope, chosen location, and any deliberate exclusions in conversation or the task handoff. No separate scope report, persona, or approval stage is needed; surface material scope decisions to the user when necessary.
- Choose implementation, review, and verification effort proportionate to the change's risk and uncertainty. Small, well-understood fixes, including localized behavior changes, can be completed directly with focused checks and self-review. Use independent review or verification when a separate perspective is likely to add meaningful confidence. Security, concurrency, cancellation, timeouts, migrations, data integrity, broad changes, release-critical behavior, and unresolved failures are reasons to consider deeper scrutiny, not automatic triggers for a fixed sequence of agents. Briefly explain the chosen approach in conversation or the PR; a small task needs no separate process record. Repository CI and release requirements remain in force.
- Before delegated implementation or independent review, use the relevant `ask-gemini` or `ask-claude` skill and run the installed adapter's local `status --provider gemini|claude --config "{{CODEX_ROOT}}/agent-framework/routing.json"` check. It reads shared last-known quota state without contacting providers. Routine implementation routes to Gemini Flash (`gemini-3.8-flash-medium`), falling back directly to native Luna medium (`gpt-6-luna`) upon Gemini quota exhaustion or non-quota failure. Review remains strictly Claude-only (`claude-opus-5-5`). An active `fallback_required` result satisfies the provider-first routing check: immediately proceed to the fallback without launching the exhausted CLI for each new operation. A `state_error` also uses the corresponding fallback with the actual error disclosed; do not erase evidence or call it confirmed exhaustion. Only `available_to_try` permits a provider attempt, and does not guarantee remaining usage. Check again on a later operation after the recorded reset or probe time; do not poll the provider while blocked. Preserve file-ownership and unresolved-run checks before handing work to a fallback. Direct small fixes do not need a provider call or task contract.
- Both provider execution paths enforce the same shared cache and record confirmed terminal usage-limit responses, reset times when unambiguous, and a bounded probe cooldown otherwise. Use the installed routing config so separate workspaces share `agent-framework/state/gemini-quota.json` and `claude-quota.json` (legacy `deepseek-balance.json` state is retained for audit/compatibility if present); do not create per-operation caches or bypass an active cache with another adapter copy. User-reported exhaustion may be recorded with `quota-set --provider gemini|claude --reason TEXT [--reset-at ISO_WITH_TIMEZONE] --config ...`; do not invent a reset time or misclassify auth, setup, pending runs, or transient throttling as exhausted usage.
- If the adapter returns `fallback_required` (exit 20), inspect the structured result: when Gemini quota is exhausted, spawn a fresh `implementer` on `gpt-6-luna` with effort `medium`. Give the replacement the original contract, existing changes, prior output and unfinished checks. Do not ask the user again. Never run competing implementation writers concurrently on the same task or overlapping files. Separate tasks with disjoint declared ownership may run concurrently, including within one workspace; directory ownership includes descendants.
- Luna medium is also the pre-authorized fallback when the checked Gemini route is unavailable or blocked, including `blocked_pending_run`; report the actual reason and proceed without another permission question. These failures are not quota exhaustion: do not falsify quota state or clear an unresolved pending run. Before handing over overlapping files, confirm the previous writer has stopped. A pending run in another workspace does not block a fresh Luna task with non-overlapping ownership. This does not bypass Codex permissions or safety review. Failed implementations route to the complex implementer when warranted.
- Complex bounded implementation: `complex_implementer`, GPT-6 Sol medium. Planning/adversarial test design: `planner`/`test_engineer`, GPT-6 Sol medium. Exploration, docs and refactor audit: Luna medium.
- Worker autonomy and handoff: Delegated workers explicitly own their assigned outcome through local investigation, implementation, focused validation, routine repairs, and self-review until criteria pass or a concrete blocker is escalated. Workers resolve ordinary implementation details, internal refactoring, test additions, and routine repairs autonomously using judgment within the contract. Escalate to the primary only for concrete blockers: material product, scope, requirements, or architectural decisions; ownership conflicts; missing authorization or unavailable prerequisites; or repeated failures requiring reassessment. Before handing over implementation, workers inspect changes for reuse, clarity, and unnecessary work, apply justified simplifications within their ownership, preserve observable behavior and others' edits, and rerun affected checks. Handoffs include completion status, changed paths, design decisions, candidate identity (e.g. HEAD plus scoped diff/status), exact checks and results, residual concerns, and useful log locations, without routine status chatter or raw command dumps. Perform this self-review pass yourself; separate review or verification is chosen by the primary according to risk.
- When independent review is useful or explicitly required, use `ask-claude` on the integrated change in fresh context after its local availability check, exactly Claude Opus 5.5, default effort medium. High effort requires a concrete complexity reason and `--review-reason`. Prefer one coherent review over per-writer and whole-branch rounds. Track material findings and their resolution; re-review repairs when uncertainty warrants it. Repeated unsuccessful repairs should prompt reassessment, not an automatic loop. Never silently waive unresolved defects. If Claude is unavailable, including cached exhaustion or exit 20 / `fallback_required` from the review route, use a fresh Astra-low `reviewer` and disclose the fallback. Never use Sonnet or Fable.
- For high-risk work, consider a scoped Sol-high `correctness_gate` when a distinct correctness question remains beyond ordinary review. Use Sol-high `security_reviewer` for explicit security analysis. Choose the depth and sequence for the actual risk; an additional gate is not automatic. GPT-6 Sol max remains exceptional user-requested deep review.
- The primary can run checks directly. Delegate verification when it adds useful independence or substantial parallel work, not merely to obtain a fresh agent. Worker claims alone are not test evidence. Reuse credible matching evidence from workers or earlier steps when relevant inputs, commands, and conditions match; do not automatically duplicate verification. Require reruns only when relevant inputs changed, evidence is missing or unreliable, explicit repository requirements mandate it, or a specific concern warrants it. Record the candidate and enough relevant input, command, configuration, and environment context to judge whether evidence still applies. For small tasks, HEAD, the scoped diff/status, and command results usually suffice. Use scoped hashes or aggregate generated-input hashes when reuse or concurrent changes warrant them; avoid exhaustive repository, dependency, ignored-file, or scratch-file inventories. Keep secrets out of records. Review output is not test evidence.
- Delegate bounded tasks with concrete acceptance criteria, explicit non-overlapping file ownership, and validation commands. Prefer compact fresh-context contracts defining full bounded outcomes; avoid tiny fragmented tasks and large history/log pastes. Subagents must not delegate again unless authorized by the parent. The integrated batch review is independent of its writers.
- Workers give a concise handoff with completion status, blockers, owned changed paths, key decisions, candidate identity, checks and results, residual concerns, and useful log locations. Avoid routine status chatter, unnecessary progress commentary, and raw log dumps. Use one compact run record only when continuity needs it; separate briefs, findings files, metrics, and worker reports are optional. Collect metrics when diagnosing workflow performance or when requested.
- User questions: When asking the user a question, identify which decision depends on their answer. Continue only work independent of that decision. Do not resolve the pending choice or treat silence as approval. If no independent work remains, wait for the user's response.
- Waiting and monitoring: Applies to the primary orchestrator and all subagents. Assign waiting and diagnosis for a delegated process, command, or CI run to one owner (the active worker executing it, or the primary when orchestrating directly with bounded waits). Do not assume another agent can access the owner's process session, and do not create nested delegation or a monitoring agent for every short command. The primary relies on completion notifications and avoids duplicate monitoring, repeated status queries, listing tasks, or redundant log reading while the worker is actively running. For native subagents, rely on completion notifications; query status only to diagnose a concrete problem or respond to a user request. For Gemini/Claude CLI tasks, prefer waiting for process completion. When polling CLI tasks or CI runs is necessary, use successive intervals of 1, 2, then 5 minutes between checks while status remains unchanged, continuing at 5 minutes thereafter. Reserve longer polling intervals for tasks explicitly expected to take a long time; CI polling remains capped at 5 minutes. Track the next check time per task or CI run. A tool returning early, a host wake-up, or a user-facing progress update does not make another status check due. Check sooner only for a completion notification, actionable error, user request, or known deadline. Reset the backoff when meaningful status changes or a new run starts. Do not send agents routine "still working?" messages. Continue useful independent work while waiting. Respect host limits on individual waits without increasing status-query frequency. Preserve required completion and CI gates.
- For native roles, use installed custom agent definitions when supported. If the host exposes only generic spawning, pass the role's exact model, effort and instructions explicitly; never assume a role label changes the inherited model. Host-supported concurrency limits take precedence.
- The user explicitly authorizes Gemini and Claude CLI approval bypass. The adapter retains legacy credential filtering and environment sanitization across subprocesses as defense in depth, not a hard same-user process containment boundary. Keep Claude limited to read/search tools and no MCP, shell, edit or subagent tools. Logs and task contracts belong in the active workspace's `.llm-output/`. Preserve partial edits; never reset or clean them automatically.

See `agent-framework/docs/FRAMEWORK.md` for invocation, reset behavior and validation limits. The archived benchmark figures are historical supplied evidence, not new measurements of Gemini or Claude.

Gemini and Claude adapter runs use stream telemetry (`stream-json`): compact step/tool transitions are emitted on stderr and written to `progress.json`, while `heartbeat.json` remains the quiet-period liveness fallback. These signals add no provider turns or provider-token cost; throttled stderr lines add a small, bounded amount to the parent agent's context. Wait for adapter completion in the same command session instead of detached `Start-Sleep` loops. A live heartbeat or recent stream event is diagnostic evidence, never proof of task correctness or authorization to start an overlapping fallback; only a terminal adapter result and resolved ownership permit handoff. Native subagents rely on completion notifications and do not need periodic prose-progress files.
